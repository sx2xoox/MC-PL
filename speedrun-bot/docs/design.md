# speedrun-bot 설계 (1·2단계, 3단계 M1)

목표: Minecraft Java 1.16.1 RSG(무작위 시드)에서 엔더드래곤까지 IGT 10분 이하. 방식: 게임 상태를 코드로 읽고 사람이
낼 수 있는 입력으로 조종하는 봇. 루트(무엇을 어떤 순서로)는 코드이고, 판단 수치(얼마나 모을지, 어디까지 우회할지,
루트 선택 가중치)는 `params.json`으로 분리해 수천 시드 반복 실행으로 자동 튜닝한다("학습"). 화면 픽셀 기반 신경망이
아니다.

이 문서: §1 아키텍처, §2 공정 규칙, §3 오버월드 루트(1단계), §4 하네스와 튜닝, §5 측정 결과(1단계), §6 단계 계획,
§7 클라이언트 포팅 계획, §8 한계와 다음 일(1단계 시점), §9 2단계(바뀐 것, 측정, 남은 격차), §10 3단계 M1(첫 네더 진입), §11 M1 2회차, §12 M1 3회차, §13 M1 4회차(바다 루트), §14 M1 5회차(바다 루트 앞쪽: 보물).

## 1. 아키텍처

```
          ┌──────────── brain (공용: 서버 전용 클래스에 의존하지 않음) ────────────┐
          │ RunBrain: 목표 선택(나무→도구→철→제련→양동이·라이터→물→용암→포탈)      │
          │ Workbench(제작 세션) · PortalBuilder · Mover(경로 따라가기) · Actions     │
          │ Navigator(A*, 기억 지도 위)  ·  Perception(시야 광선) → WorldMemory      │
          │ Controls: 사람 입력 상한(회전 속도, 클릭 간격) 적용                      │
          └───────────────▲───────────────────────────────┬────────────────────────┘
               BotSenses (본 것·자기 상태)            BotInputs (키·마우스·레시피북)
          ┌───────────────┴───────────────────────────────▼────────────────────────┐
          │ server: ServerBot = FakePlayer(ServerPlayerEntity 하위) + FakeConnection │
          │ (나중) client: ClientPlayerEntity 입력 주입 + ClientWorld  (§7)          │
          └─────────────────────────────────────────────────────────────────────────┘
core (순수 로직, MC 무관): MiningTime, Igt, InputLimits, PerceptionRules, Params, RouteSelector, PortalPlan, Cell
```

**왜 Fabric 1.16.1 서버 + 가짜 플레이어인가.** 봇이 진짜 `ServerPlayerEntity`라서 이동 물리(점프·달리기·낙하),
채굴 시간(서버 `ServerPlayerInteractionManager`의 진행 검사), 피해, 허기, 인벤토리·제작(스크린 핸들러), 포탈 이동이
전부 바닐라 코드 그대로다. 봇이 따로 흉내 내는 것은 "클라이언트가 보내는 입력"뿐이다. 클라이언트(LWJGL/렌더링)가
없어 헤드리스로 여러 서버를 병렬 실행할 수 있다. 착안은 Carpet mod의 `/player` 가짜 플레이어(MIT)이고 코드는
1.16.1 Yarn 이름으로 새로 작성했다(`server/FakePlayer`, `FakeConnection`).

- 가짜 플레이어: 실제 서버 플레이어는 클라이언트 패킷이 움직이지만, 가짜 플레이어는 `tick()`에서 `playerTick()`을
  돌려 서버가 직접 `LivingEntity#tickMovement → travel`로 움직인다. 5틱마다 청크 시야 갱신(`updateCameraPosition`).
  서버 플레이어는 낙하 피해를 클라이언트 보고로 받기 때문에 `fall()`을 `handleFall()`로 연결했다. `stepHeight`는
  클라이언트 값 0.6(서버 기본 1.0이 아님).
- 입력 구현(`ServerBot`): 이동 = `forwardSpeed/sidewaysSpeed/jumping/sprinting/sneaking`, 시점 = yaw/pitch, 채굴 =
  바닐라 클라이언트와 같은 진행 누적(매 틱 `calcBlockBreakingDelta`를 float로 더해 1 이상이면 STOP_DESTROY_BLOCK,
  이어서 5틱 쿨다운) → 서버는 자기 틱 수로 다시 검사하므로 빨리 캘 수 없다. 우클릭 = `interactBlock/interactItem`
  (크로스헤어 = `rayTrace(4.5)`), 화면 = `onSlotClick`, 레시피북 = `fillInputSlots`(레시피북에 해금된 레시피만).
- 틱 워프: `MinecraftServer#shouldKeepTicking`을 믹스인으로 바꿔 틱 사이에 잠자지 않는다(Carpet `/tick warp`와 같은
  방식). 틱 자체는 그대로 다 실행되므로 게임 동작과 틱 기반 IGT는 바뀌지 않는다. 실측 약 100~200 TPS(4 CPU, 서버
  4개 병렬 시).
- 런 1회 = 서버 시작 1회(`BotRuntime`): 첫 틱에 봇이 접속(일반 플레이어처럼 월드 스폰에서, `spawnRadius 0`으로
  재현성 확보), 매 틱 두뇌 실행, 끝나면 결과 JSON 한 줄을 쓰고 JVM 종료(월드는 버린다).

**두뇌를 인터페이스 뒤에 둔 이유.** 같은 봇을 나중에 사용자 화면(1.16.1 Fabric 클라이언트 싱글플레이)에서 그대로
돌리기 위해서다. `brain/`은 `BotInputs`(사람이 클라이언트에서 낼 수 있는 단위의 입력: 이동/점프/달리기/웅크리기,
시점, 공격 누름·엔티티 공격, 사용, 핫바, 인벤토리 열기, 화면 슬롯 클릭, 레시피북 클릭, 화면 닫기)와
`BotSenses`(자기 상태·인벤토리·열린 화면·크로스헤어·게임 틱 + `Perception`만 쓰는 블록/엔티티 접근)만 본다.
`brain/` 패키지는 `ServerPlayerEntity`, `ServerWorld` 등 서버 전용 클래스를 import하지 않는다(블록 상태, 아이템,
스크린 핸들러 같은 공용 클래스만 사용). 또 빌드가 서버 jar만 보고 컴파일하므로(`serverOnlyMinecraftJar`) 클라이언트
전용 메서드가 섞이면 컴파일이 실패한다.

**참고한 설계.** 길찾기는 Baritone(LGPL)의 개념(이동 종류별 비용, 채굴 시간을 비용으로, 부분 경로 후 재계획)을
참고했지만 코드는 새로 썼다. MC-PL 증강 봇(`game/augment/bot`)에서 "순수 판단기 + 몸(컨트롤러) 분리" 구조를 가져왔다.

## 2. 공정 규칙 (기본 켜짐)

| 규칙 | 구현 | 테스트 |
|---|---|---|
| 본 것만 안다 | `Perception`: 매 틱 눈 위치에서 시야(세로 FOV 70°, 16:9 → 가로 약 102°) 안으로 무작위 광선 220개 + 크로스헤어 광선 1개. 광선은 불투명 정육면체와 용암에서 멈추고, 지나간/멈춘 블록만 `WorldMemory`에 기록. 렌더 거리(기본 10청크) 상한, 로드 안 된 청크에서 정지. 몸에 닿는 3×4×3 블록은 항상 감지 | `CoreLogicTest.viewFrustumAndRenderDistance`, `sampledRaysStayInsideTheFrustum` |
| 세계를 직접 보지 않는다 | 판단·길찾기·목표 선택은 `WorldMemory`만 읽음. 청크 스캔, 구조물 위치 조회, 시드 읽기, 월드 생성 미리 실행 없음. 엔티티도 시야 안 + 블록 시선이 트인 것만 | 코드 구조(`brain`은 `BotSenses.blockAt`을 `Perception`에서만 호출) |
| 사람 입력만 | 시점 회전 45°/틱(900°/s), 피치 35°/틱, 블록 도달 4.5칸, 엔티티 3칸, 사용 클릭 4틱 간격(바닐라 itemUseCooldown), 화면 클릭 2틱(100ms) 간격, 화면 열기 2틱, 핫바 변경 1회/틱, 공격·사용 1회/틱, 달리기는 배고픔 > 6이고 앞으로 갈 때만 | `turningIsRateLimitedAlongTheShortestWay` |
| 채굴 시간 = 바닐라 | 서버 interaction manager를 거침 + 클라이언트식 float 누적 + 5틱 쿨다운 (`MiningTime`이 같은 식으로 비용 추정) | `stoneWithWoodenPickaxe` 외 4개 (float 누적 때문에 원목 맨손 61틱 등 실제 클라이언트 값) |
| IGT | `Igt`: 봇 접속 틱부터 서버 틱 수 / 20. SpeedRunIGT(1.16.1)는 일시정지·로딩을 뺀 월드 진입~최종 이벤트 시간이고 봇은 일시정지가 없으므로 같다. 서버가 틱당 50ms를 넘겨도(MSPT>50) IGT는 틱 기준이라 영향 없고, MSPT는 결과에 따로 기록 | `igtCountsServerTicksFromWorldEntry` |
| 물 속 시야 (2단계) | 시야 광선이 물 블록을 16칸 넘게 지나가면 끝난다(바닐라 클라이언트의 물 안개). 난파선·바다 바닥도 이 거리 안에서만 보인다 | `Phase2LogicTest.waterFogEndsSightRays` |
| 지도 읽기 (2단계) | 보물 지도는 손에 들었을 때 화면에 그려지는 표식(자기 표식, 빨간 X, 지도 축척)만 `BotSenses.heldMap()`으로 읽는다. X 위치 = 자기 위치 + (X 표식 − 자기 표식) × 축척. 자기 표식이 지도 밖이면 방향만 안다. 구조물 위치 조회 없음 | `treasureMapPointsAtTheChunkOffsetNineNine`(바닐라 표식 공식으로 검증), `offMapPlayerOnlyGetsADirection` |
| 좌표 (2단계) | 자기 좌표(F3, 사람도 언제나 볼 수 있음)로 보물을 청크 안 9,9 칸에서 판다(1.16 매장 보물 위치 규칙, 사람 러너와 같은 지식) | 같은 테스트 |
| 상자·구조물 (2단계) | 상자는 시야 광선에 걸린 것만 연다(`Looter`). 난파선은 물속/물가에 붙은 가공 목재(판자·계단·반블록·울타리·다락문) 묶음을 본 것으로 판단 | 코드 구조 |
| 아이템 사용 규칙 (2단계) | 우클릭은 바닐라 서버 경로 그대로: 블록이 클릭을 먹으면(레드스톤 광석이 빛남 등) 손의 아이템은 쓰이지 않는다 → 그런 면에는 양동이를 붓지 않는다 | 실전 디버깅(주조 단계) |
| 소리 (3단계 M1) | 용암 소리만 듣는다. 바닐라 1.16.1 클라이언트가 매 틱 하는 무작위 표시 틱(플레이어 둘레 ±16·±32칸에서 667번씩)을 그대로 흉내 내, 위가 공기인 용암 블록이 `block.lava.pop`(1/100)·`block.lava.ambient`(1/200)를 낸 경우만, 16칸 안(볼륨 1 이하 소리의 들리는 거리)이면 듣는다. 벽 너머도 들린다(마인크래프트에 소리 가림 없음). 봇이 받는 것은 블록 위치가 아니라 사람이 귀로 아는 정도: 방향(좌우 표준편차 15°, 위아래 25°)과 소리 크기로 짐작한 거리(상대 오차 표준편차 30%). 헤드리스 서버에는 소리 엔진이 없어 서버에서 같은 확률로 흉내 내고(`core/Hearing`, `ServerBot.heardLava`), 클라이언트 포팅에서는 실제로 재생되는 소리 이벤트를 읽으면 된다. `-Dsrb.hearing=false`로 끈다 | `HearingTest.lavaIsHeardOnlyWithin16Blocks`, `perceivedSoundsAreRoughButCentredOnTheSource` |
| F3 파이 차트 (3단계 M1 3회차) | 바닐라 1.16.1 디버그 프로파일러의 "blockentities" 조각: 상자는 엔티티 모델로 그려져서 상자가 카메라 시야 절두체 안·렌더 거리 안에 있으면 조각이 커진다. 클라이언트는 블록 엔티티를 절두체로만 거르고(가림 검사 없음) 그리므로 지형에 묻힌 상자도 센다. 봇이 받는 것은 지금 시야 절두체 안 상자 수(조각 크기)뿐이고 위치는 없다(`core/PieChart`, `BotSenses.pieChests`). 시야 설정: FOV 옵션 30~110과 창 비율(가늘고 긴 창 = 좁은 가로 시야); 바꾸는 데 20틱(사람이 옵션·창 크기를 바꾸는 시간, 그동안 다른 입력 없음). 매장 보물 위치는 이 방위 측정 + F3 좌표 + 1.16의 청크 9,9 규칙(공개 지식)으로만 정한다 | `PieChartTest.frustumTestMatchesTheViewDirection`, `narrowWindowNarrowsTheHorizontalFov`, `sweepsFromTwoPlacesFindTheTreasureColumn` |
| 리셋 판단 (RSG) | 사람 러너처럼 나쁜 시드를 버리는 판단을 본 것만으로 한다(`core/ResetPolicy`: 스폰에 나무·바다 없음, 바다인데 보물 신호·나무 없음, 철·물·포탈 터 구간이 늦음). 시드별 측정은 멈추지 않고(비교 가능성) 첫 판단의 틱과 이유만 기록한다 | `PieChartTest.resetPolicyUsesOnlyWhatWasSeen` |
| 보트 (4회차) | 바닐라에서 탄 보트의 물리는 타는 사람의 클라이언트가 돌린다. 봇이 탄 보트에 한해 서버가 같은 클라이언트 코드(`updatePaddles`)를 봇이 누른 키(W/A/D)로 돌린다(`mixin/BoatEntityMixin`). 타기 = 엔티티 우클릭, 내리기 = 웅크리기. 감각은 탄 보트의 방향만 | 개발 고정 장면(§13.3) |
| 물속 웅크리기·수영 달리기 (5회차) | 바닐라 클라이언트가 하는 두 가지를 서버의 봇 몸에 그대로 옮겼다: 물속에서 Shift를 누르면 매 틱 아래로 0.04(`ClientPlayerEntity#tickMovement` → `knockDownwards`; 전에는 서버가 이 클라이언트 코드를 돌리지 않아 봇이 웅크려도 가라앉지 않았다), 물에서 달리기는 눈이 물에 잠겼을 때만 시작(같은 메서드의 규칙; 수영 자세가 되면 수면에서도 유지) | 개발 고정 장면(§14.2) |
| 레시피 (5회차) | 레시피 북은 바닐라처럼 해금된 것만 쓴다(재료를 처음 가지면 인벤토리 화면이 그것을 볼 때 해금, 보트는 물에 들어가 본 뒤에야 해금). 해금 전이면 사람처럼 손으로 격자에 놓는다(집기 → 칸마다 우클릭 한 개 → 내려놓기, 클릭마다 2틱 간격). 레시피 모양은 공개 게임 지식(`BotSenses.allCraftingRecipes`), 월드 상태 아님 | 실전 trace(§14.2) |
| 매장 보물 바닥 규칙 (5회차) | 1.16 `BuriedTreasureGenerator`: 상자는 9,9 칸을 위에서 내려가다 아래 블록이 돌·사암·안산암·화강암·섬록암인 첫 자리에 놓인다(공개 생성 지식). 그 칸을 파다 이 블록이 나오면 상자는 그 칸에 없다 | `TreasureHunt.treasureFloor` |
| 보물 칸 확인 (5회차) | 같은 파이 차트 감각: 후보 9,9 칸 바로 위(보트·물 위 1칸 안)에서 좁은 시야로 칸을 내려다보며 상자 조각이 생기는지 본다(위치는 받지 않음, 절두체 안 상자 수뿐) | `TreasureHunt.verify` |
| 십자 확인 (6회차) | 같은 감각: 후보 칸 위에 서서(칸 안) 피치 90°, 가는 창을 요 0°·90° 두 번 본다(사람이 마우스로 하는 것과 같은 시선 두 개). 두 번 모두 조각이 있어야 확인. 하네스의 월드 덤프(`srb.probeDump`)는 오프라인 시뮬레이터 전용이고 봇은 읽지 않는다 | `TreasureHunt.verify`, `PieChartTest.columnsOnlyOnePlaceSawAreNoCandidatesWithMinVotes` |
| 거품 기둥 (4회차) | 마그마 위 거품 기둥은 시야 광선이 지나간 칸만 기억(물 안개 16칸 그대로). 협곡 바닥 y 10 = 마그마/흑요석, 그 밑 = 용암은 공개 생성 지식으로만 쓴다 | 코드 구조 |
| 요새 삼각측량 | 3단계에서 엔더 눈 두 번 던지기로 구현 예정(눈 엔티티의 비행 방향만 관찰) | - |
| 비교용 완화 모드 | `-Dsrb.fair=false` 또는 `run_batch.py --relaxed`: FOV 무시(구 전체 광선) + 40틱마다 주변 24칸 정육면체 직접 읽기. 비교 측정 전용 | - |

결정성: 봇의 무작위(광선 샘플, 탐색 방향)는 시드 기반 `Random`이다. 서버 쪽 무작위(몹 스폰, 드롭, 자갈→부싯돌
확률)는 바닐라 그대로라 같은 시드도 런마다 결과가 조금 다르다.

## 3. 오버월드 → 네더 진입 루트 (1단계)

### 3.1 목표 순서 (`RunBrain.choose`)

1. **SCAN** (`surface.scanTicks`): 제자리에서 주변을 둘러봄 → 루트 선택기 입력 수집.
2. **WOOD**: 기억 지도의 가장 가까운 원목(발 높이+6 이하)으로 가서 캔다. 없으면 무작위 방향 탐색. `wood.logs`개.
3. **WOOD_TOOLS** (Workbench 세션): 원목 → 판자(레시피북), 2×2에서 제작대, 설치, 막대·나무 곡괭이.
4. **COBBLE → STONE_PICK**: 노출된 돌을 캐거나 1×2 계단식으로 파 내려감. 돌 곡괭이 `stone.picks`개(131블록 내구도).
5. **IRON**: `dig.targetY`까지 계단식 하강 후 1×2 터널. 보이는 철광석(우회 `dig.oreDetour`), 자갈(`dig.gravelDetour`),
   석탄을 캔다. 철 4개(양동이 3 + 부싯돌과 부시 1).
6. **SMELT**: 화로 제작·설치, 광석 + 연료(석탄 → 판자 순) 투입, 대기, 꺼냄.
7. **IRON_TOOLS**: 양동이, (부싯돌이 있으면) 부싯돌과 부시. 부싯돌은 자갈을 캐고, 자갈만 나오면 내려놓고 다시 캐서
   얻는다(1회 10%).
8. **WATER**: 기억 지도의 물 원천(위가 트인 것)으로 가서 양동이에 담음.
9. **LAVA**: 위가 트인 용암 원천을 기억 지도에서 찾음. 없으면 지하 탐색 계속.
10. **PORTAL** (`PortalBuilder`): 아래 3.3 버킷 주조.
11. 포탈에 들어가 네더 도착 → 성공.

같은 순서가 두 루트를 다룬다. 루트 선택기(`RouteSelector`, 단위 테스트 있음)는 SCAN 뒤 기대 시간(초) 모델로
고른다: `DIG_CAST` = `route.digBaseSec` + 물까지 거리 × `route.secPerBlock`; `SURFACE_CAST`(지표 용암 웅덩이가
`surface.lavaMaxDist` 안에 보일 때) = `route.surfaceBaseSec` + 용암 거리 + 모자란 철 × `route.ironMissingSec` + 용암~물
거리 × 2. SURFACE_CAST는 철을 위해 y≈40까지만 내려가고 그 웅덩이 옆에 포탈을 짓는다. 가중치는 튜닝 대상.

### 3.2 이동과 채굴

- `Navigator`: 기억 지도 위 A*. 모르는 칸은 로봇 항법의 free-space 가정(몸 칸은 통과 가능, 바닥은 있다고 보되 작은
  추가 비용) → 새로 보이는 대로 재계획. 이동: 8방향 걷기, 1칸 오르기(점프), 1~3칸 내려가기(첫 칸은 파기 허용 =
  계단), 아래로 파기, 기둥 쌓기, 수영. 막힌 칸은 가진 도구 중 가장 빠른 것의 바닐라 채굴 틱을 비용으로 판다. 용암을
  여는 파기는 금지, 용암 옆 칸은 큰 비용.
- `Mover`: 경로를 입력으로 따라감(조준·전진·달리기·점프, 막힌 칸은 위부터 캠), 막힘·이탈·낙하 위험이면 재계획.
- `Actions.mine`: 가장 빠른 도구 장착 → 블록 면 중심 조준 → 크로스헤어가 그 블록이면 공격 누름. 사이에 풀·잎 같은
  가림막이 있으면 그것부터 캔다(사람처럼 계속 조준한 채).
- `Workbench`: 제작 세션 하나가 시작~끝까지 화면을 소유(제작대가 바로 옆에 없으면 새로 설치, 판자·막대 부족분을
  먼저 제작). 클릭은 모두 `Controls`의 간격 제한을 받는다.

### 3.3 버킷 포탈 주조 (`core/PortalPlan` + `brain/PortalBuilder`)

양동이 하나로 단단한 암반 속에 4×5 틀(모서리 제외 흑요석 10개)을 만든다.

1. 용암 원천에서 `portal.maxLavaDist` 안, 틀·내부·뒤판이 아는 한 전부 단단한 블록이고 용암·물·떨어지는 블록이
   붙어 있지 않은 자리를 고른다(4방향 × 좌우 × 높이 탐색, 모르는 칸이 적을수록 좋음).
2. 틀 앞에 방(앞 1칸 깊이, 서 있는 줄 2칸 높이)을 판다. 서 있는 줄 바닥에 물 대기 구멍(1칸)을 파고 물을 부어 둔다.
3. 틀 칸마다(바닥 2 → 양 기둥 아래부터 6 → 위 2): (바닥은 앞 바닥 구멍을 먼저 파고) 그 칸을 파서 주머니를 만든다
   — 다섯 면이 암반·흑요석이라 용암이 앞쪽 말고는 흐를 데가 없다. 빈 양동이로 용암 원천을 떠 와서 주머니 안쪽
   면을 클릭해 붓고, 바로 물 대기 구멍의 물을 떠서 주머니 앞 칸에 붓는다(물이 닿은 용암 원천 = 흑요석; 용암은
   30틱 뒤에야 흐르므로 그 전에 닿는다). 물을 다시 떠서 대기 구멍에 돌려놓는다. 바닥 구멍은 조약돌로 메운다.
4. 내부 6칸을 캐고, 아래 흑요석 윗면에 부싯돌과 부시 → 포탈 → 들어감.

계획의 기하(틀 10칸, 주조 순서, 각 칸이 부을 때 막혀 있어야 할 이웃이 방에 속하지 않음 등)는
`CoreLogicTest.portalPlanGeometry`, `castOrderKeepsEachPocketClosed`가 검사한다.

## 4. 하네스와 튜닝

- `tools/setup_server.py --accept-eula`: Fabric server launcher(로더 0.20.1)를 받고 한 번 띄워 1.16.1 서버 jar와
  라이브러리를 받아 `work/template`을 만든다. EULA는 사용자가 직접 동의해야 하며 플래그 없이는 `eula.txt`를 쓰지
  않는다.
- `tools/run_batch.py`: 슬롯(서버 디렉터리) N개를 병렬로 돌린다. 시드마다 `server.properties`(시드, 포트, view-distance
  10, easy) 작성 → `world` 삭제 → 서버 실행 → 봇 1회 런 → 결과 JSON → CSV/JSONL 누적. 판단 로그(`--trace-dir`)는
  목표 전환, 구간 기록, 10초마다 상태(위치·체력·배고픔·인벤토리)를 남겨 실패 원인을 찾는 데 쓴다.
- 결과 CSV: 시드, 성공, 실패 이유, 루트, 최종 IGT, 구간 IGT(`first_log, wooden_pickaxe, stone_pickaxe, first_iron,
  furnace, iron_ingots, bucket, flint, flint_and_steel, water_bucket, portal_site, portal_room, obsidian_10, portal_lit,
  in_portal, nether`), MSPT 평균·최대, 실제 걸린 시간.
- `tools/tune.py`: 교차 엔트로피 방식(CMA-ES의 단순형). `tools/param_space.json`의 범위를 [0,1]로 정규화하고, 세대마다
  현재 평균 주변에서 후보를 뽑아 **같은 고정 시드 집합**(`tools/seeds_tune.txt`, 공통 난수로 분산 감소)에서 돌린다.
  점수(낮을수록 좋음) = 네더 진입이면 IGT 초, 아니면 제한 시간 + 못 간 구간마다 60초. 상위(elite) 후보 쪽으로 평균과
  표준편차를 옮긴다. 0세대에는 기준(현재 기본값)이 반드시 포함된다. 아직 네더 진입이 드물기 때문에 "구간 도달"
  점수가 기울기를 준다.

## 6. 단계 계획

1. **(이번) 오버월드 → 네더 진입**: 기반, 공정 규칙, 하네스, 버킷 주조 루트, 튜닝 루프.
2. **네더**: 바스티온 찾기(시야 기반: 블랙스톤·금 블록·바스티온 특유 블록 군집), 금괴 → 피글린 물물교환으로 엔더 진주
   (금 투척, 교환 대기·회수, 몹 회피), 요새 탐색(네더 요새 벽돌 군집, 직선 탐색 + 시야), 블레이즈 막대(스포너 근처
   전투), 귀환 포탈(네더 포탈 재사용 또는 새로 주조). 판단 수치: 진주·막대 목표 개수, 교환 시간 상한, 탐색 방향 가중치.
3. **엔드**: 엔더 눈 제작, 오버월드에서 눈 두 번 던져 삼각측량(관찰된 비행 방향 두 직선의 교점), 요새 진입·엔드 포탈
   방 찾기(지하 탐색), 드래곤 원사이클(침대 폭발 또는 수정 처리 후 원사이클, 1.16.1 기준). 각 단계는 같은 하네스에서
   구간 IGT로 측정·튜닝.

## 7. 클라이언트 포팅 계획 (사용자 화면에서 같은 봇 돌리기)

이번 단계에서는 만들지 않는다. 두뇌(`brain/`, `core/`)는 그대로 쓰고 `BotInputs`/`BotSenses`의 클라이언트 구현만 추가한다.

- 입력(`ClientBotInputs`): 이동·점프·달리기·웅크리기는 `KeyBinding`의 눌림 상태를 매 틱 설정(또는
  `ClientPlayerEntity.input`(`KeyboardInput`)을 덮어쓰는 믹스인) → 클라이언트 예측 이동과 서버 검증이 바닐라 그대로
  일어난다. 시점은 `player.yaw/pitch`(마우스 이동과 같은 효과). 공격 누름은 `options.keyAttack` 상태(블록 채굴은
  `ClientPlayerInteractionManager`가 직접 진행) 또는 `attackBlock/updateBlockBreakingProgress` 호출. 사용은
  `interactBlock/interactItem`(= `doItemUse`), 핫바는 `inventory.selectedSlot`, 화면은 `clickSlot`,
  `clickRecipe`(레시피북), `closeHandledScreen`, 인벤토리는 `InventoryScreen` 열기.
- 인지(`ClientBotSenses`): `ClientWorld`의 로드된 청크에서 블록 상태, `MinecraftClient.crosshairTarget`, 자기 상태는
  `ClientPlayerEntity`, 열린 화면은 `player.currentScreenHandler`, 레시피북은 `ClientRecipeBook`, 게임 틱은
  `world.getTime()` 또는 클라이언트 틱 카운터(IGT는 SpeedRunIGT와 같은 기준으로 계산).
- 차이점과 대응: (1) 클라이언트 예측 이동 — 입력 결과가 서버와 1틱 어긋날 수 있다(경로 추종은 이미 위치 피드백
  기반). (2) 화면 열기 지연 — 제작대·화로를 우클릭하면 서버 응답(OpenScreen 패킷)까지 1~2틱+핑이 걸린다:
  `Controls`의 화면 열기 대기 상수를 실제 열림 확인으로 바꾼다(지금도 열린 화면 타입을 확인하고 진행). (3) 슬롯
  클릭은 클라이언트가 예측하고 서버가 확정 → 결과 확인 후 다음 클릭. (4) 렌더 거리·청크 로딩은 클라이언트 설정을
  따름(공정 규칙의 렌더 거리와 동일). (5) 틱 워프 없음(실시간), 싱글플레이 통합 서버. (6) 사람이 언제든 끼어들 수
  있게 키 하나로 봇 정지/재개.

## 8. 한계와 다음 일

정직한 현재 상태: **아직 네더 진입에 성공한 런이 없다.** 기반(가짜 플레이어, 공정 인지, 길찾기, 채굴, 제작, 제련,
하네스, 튜너)은 동작하고, 대부분의 시드에서 나무 → 도구 → 철 → 화로 → 양동이까지는 간다. 막힌 지점(우선순위 순):

1. **철 찾기가 느리다.** 1×2 계단·터널은 벽면만 보여서 광석 노출이 적다(중앙값 첫 철 ~2.5~3.5분, 상위 러너는 1분
   안팎). 다음: 동굴·협곡 우선 탐색(시야에 큰 공기 공간이 보이면 그쪽으로), 난파선·폐허 포탈·마을 상자(지표에서
   보이는 구조물 블록 패턴 인식), 철 골렘. 지표 철(노출 광석) 우선 경로.
2. **물과 용암이 멀다.** 지하에서 양동이를 만든 뒤 물을 찾아 지표까지 다시 올라가는 데 수 분이 걸린다. 다음: 하강
   시작점을 물 근처로(SCAN에서 본 물), 지하 물(동굴 물 원천) 기억 활용, 지표 용암 웅덩이 루트(SURFACE_CAST)
   비중 확대.
3. **포탈 주조 단계는 실제 월드에서 끝까지 검증되지 않았다.** 계획 기하는 단위 테스트를 통과하지만, 측정 중 이
   단계까지 도달한 런이 아직 없어 실행기(`PortalBuilder`)의 실전 버그가 남아 있을 가능성이 크다.
4. **생존**: 스켈레톤 화살, 좀비, 크리퍼, 용암, 익사(모래·자갈이 떨어진 물 구덩이)로 죽는다. 근접 반격만 있고
   원거리 회피·방패·후퇴·식사가 없다.
5. **상호작용 견고성**: 화면(제작대·화로)·핫바 교체·블록 설치가 서로 화면을 닫는 경쟁을 여러 번 고쳤다(제작 세션,
   화면 잠금). 아직 시선이 막힌 제작대/화로를 못 여는 경우가 남아 있다(새로 설치로 우회).
6. **성능**: 서버 1개당 실제 100~200 TPS(4 CPU, 4개 병렬, 대부분 청크 생성 비용). 10분 IGT 한 런 ≈ 1.5~2.5분 실제 시간
   + 서버 시작 ~20초. 4병렬로 시간당 약 100런. 수천 시드 튜닝에는 하루 단위가 필요 → 다음: 스폰 영역 준비
   축소(봇 시작에는 무관), JVM 재사용(한 서버에서 월드 교체), 광선 수 조절.

## 9. 2단계: 네더 진입 신뢰성, 보물 루트, 처리량

2단계 목표는 (1) 네더 진입을 안정적으로 만들기, (2) 처리량, (3) (1 달성 시) 네더 진행이었다. 결론부터: **(1)의
목표(평가 시드 48개 중 50% 이상 네더 진입)에는 도달하지 못했다.** 단계별 병목(화면 경쟁, 화로, 포탈 주조 실행기,
물 확보)을 실전에서 하나씩 찾아 고쳤고 앞 단계 도달률·속도는 올랐지만, 런 하나가 끝까지 가려면 열 단계 가까이가
연달아 성공해야 해서 아직 네더 진입은 평가 시드 48개 중 0개 이다. (3)은 시작하지 않았다. 아래는 무엇을 바꿨고, 무엇을
측정했고, 무엇이 남았는지다.

### 9.1 바뀐 것

**화면 소유권(1단계 실패 1위였던 제련 시간 초과의 근본 원인).** 화면을 여는 일은 이제 상태 기계 하나가 열기부터
닫기까지 소유한다: `Workbench`(제작), `Smelter`(화로), `Looter`(상자). 셋 중 하나가 화면 단계에 있으면
`RunBrain.run()`은 그 세션만 실행하고, 목표 전환(`choose`)도 그동안 멈춘다. 채굴(`Actions.mine`)은 더 이상 남의
화면을 닫지 않는다. 핫바 교체용 인벤토리 열기(`Actions.equip`)는 호출자가 5틱 넘게 다시 부르지 않으면 스스로
풀린다(1단계에서 목표가 영구히 얼어붙던 원인). 싸움이 나면 `Survival`이 세션을 `interrupt()`로 깨끗이 접고,
세션은 다음 호출에서 걷기부터 다시 한다.

**`Smelter`.** PLACE → GO → OPEN → LOAD → CLOSE → (다른 일) → GO_COLLECT → OPEN → COLLECT → CLOSE. 연료는 필요한
만큼만 넣는다: 스택을 집어 연료 칸에 우클릭 한 번씩(석탄 1개 = 8개, 판자·원목 1개 = 1.5개), 나머지는 원래 칸으로
되돌린다(1단계는 판자 한 스택을 통째로 넣어 나무가 모자랐다). 석탄 → 예비분을 넘는 판자 → 원목 순. 화로가
안 열리면(크로스헤어가 안 닿음) 화로 바로 옆 칸으로 가서 다시 연다. 기다리는 동안은 화로 근처 자갈에서 부싯돌을 캔다.

**제작대 관리와 나무.** 판자 예비분(`plankReserve`)을 남기고 연료로 쓰고, 앞으로 제작이 남았는데(양동이·부싯돌과
부시) 새 제작대를 만들 나무가 모자라면 제작대를 다시 캐서 들고 간다(`Workbench` PICKUP). 기존 제작대 재사용 거리
6 → 16. 나무가 다 떨어지면 실패 대신 나무(나무, 또는 지하에서 본 갱도·난파선 판자)를 다시 구하러 간다.
제작대 세션에서 곡괭이가 하나뿐이면 예비 돌 곡괭이를 같이 만든다. 나무 찾기는 한 방향을 유지하고(무작위 회전은
스폰 주위만 맴돌았다), 본 나뭇잎 쪽으로 간다.

**철 찾기.** (a) 동굴 프런티어 탐색(`core/Frontier`, 단위 테스트): 기억 지도에서 "지붕 아래의, 넓은(자기가 판
1×2 터널이 아닌), 아직 안 본 칸과 맞닿은, 서 있을 수 있는 공기 칸"을 고르고 걸어가서 360° 둘러본다. 지표 높이보다
8칸 이상 아래만(나무 그늘은 동굴이 아님). (b) 트인 곳(절벽, 동굴 벽)에서 본 철광석은 40칸까지 걸어간다.
(c) 지표에서 y 45까지는 1×1 수직 굴(가장 빠름), 그 아래는 계단. 철 높이 `dig.ironY` 35 → 50(물까지 다시 올라가는
거리 단축; 철은 y 0~64 균등).

**물과 등반.** 양동이를 만든 뒤 물이 4칸 넘게 위에 있으면 길찾기 대신 곧장 위로 오른다(`Mover.climb`: 머리 위를
캐고, 점프해서 발밑에 블록을 놓는다, 기둥 쌓기 버그 수정: 이전 단계 상태가 남아 기둥이 멈췄다). 지표에 올라 굴
밖으로 나갈 수 있을 때까지 오른다. 몸에 닿은 물·머리 위 물은 걷지 않고 바로 뜬다. 용암을 찾아 내려갈 때는 물을 뜬
호수에서 12칸 떨어진 곳에서 판다(호숫가 계단은 물에 막혀 맴돌았다). 물에 떠 있으면 먼저 마른 땅으로 나간다.

**용암과 포탈 주조(실전 검증).** 개발용 키트(`-Dsrb.kit`, `-Dsrb.devStart=lavalow`: 하네스가 월드를 읽어 용암
옆으로 순간이동, 결과에 `dev` 표시, 측정에는 안 씀)로 주조 단계만 반복 실행해 실제 월드에서 고친 것:
- 모르는 칸(바위 속)을 캘 때 크로스헤어 앞 블록부터 판다(1단계: 모르는 칸은 20틱 뒤 실패 → `mine_failed`).
- 용암은 양동이 자신의 광선(원천만 맞는 광선)이 원천을 가리킬 때만 뜬다. 그 위치는 "용암 높이 이상에 서서 원천 윗면이
  보이는 곳"(`Navigator.see`).
- 물을 붓는 면이 레드스톤 광석이면 블록이 클릭을 먹어 양동이가 안 쓰인다(바닐라 규칙) → 그런 면은 피한다.
- 세 번째 줄 앞칸이 서 있는 줄에서 안 보였다 → 방에 머리 높이 칸 추가(`PortalPlan.room`).
- 모든 틀 칸에 물을 붓는 면이 있어야 한다(`frontSupports`, 테스트) → 없으면 조약돌로 만든다. 주머니 뒤가 동굴이면
  조약돌로 막는다.
- 터가 실패하면 대기 구멍의 물을 다시 떠서 간다. 반쯤 만든 틀은 용암이 떨어져도 버리지 않고 근처에서 더 찾는다.
- 터는 용암과 같은 높이(용암 뜨기가 짧은 걸음), 멀리 본 용암은 먼저 20칸 안으로 다가간 뒤 터를 고른다.
- 칸마다 주조 사이클은 실전 약 4초(용암 뜨기 → 붓기 → 물 뜨기 → 붓기 → 다시 뜨기 → 대기 구멍).
  dev 키트 측정에서 흑요석 10개 중 6~9개까지 실제로 만들어졌다.

**생존(`Survival`).** 가까운 적대 몹 근접 공격(가장 센 도구), 맞았으면 6칸 안 적도 공격, 크리퍼는 심지가 타거나
체력이 낮으면 물러남, 화살을 맞으면 보이는 스켈레톤에 돌진(체력 여유) 또는 시야 밖으로 후퇴. 용암에 빠지면 물
양동이를 발밑에 붓고(나중에 다시 뜸) 아는 용암 반대 방향으로 탈출. 머리가 자갈·모래에 묻히면 캐냄. 공기 부족이면
위로 헤엄. 배고프면 먹고, 아주 배고프면 동물을 잡는다. 길찾기는 용암이 몸(발·머리) 옆이나 머리 위에 있는 칸에
절대 서지 않고, 1칸 넘게 떨어질 때는 착지점을 먼저 본다.

**감시견.** 300틱 동안 위치(물 위 출렁임 제외)와 인벤토리가 그대로면 하위 상태(목표 블록, 동굴 목표, 길)를 버리고
잠깐 무작위 방향으로 걷고 점프하고 앞을 판다. 무엇을 하다 멈췄는지(`act`)를 판단 로그에 남긴다.

**보물 루트(바다 스폰, 사람 러너의 루트).** `RouteSelector`에 `TREASURE` 경로(기대 시간 = `route.treasureBaseSec` +
난파선 거리 × 초/칸). SCAN 또는 이후 걷는 중에 난파선을 보면(물에 닿은 가공 목재 6개 이상 묶음, y 35~70, 근처에
큰 물: 갱도 오탐 방지) 철을 캐는 대신: 난파선 둘레를 돌며 보고 → 보인 상자를 열어(`Looter`: 철, 금, TNT, 음식, 석탄,
지도, 부싯돌과 부시, 흑요석...) → 안 보이면 선체 판자를 뜯어 안을 보고 → 지도를 손에 들어 표식을 읽고(`core/
TreasureMap`) → X 쪽으로 걸어가며 다시 읽고 → 청크 9,9 칸에서 아래로 파서 → 보인 상자를 연다. 보물의 철이 4개
이상이면 채굴·제련을 건너뛰고 바로 양동이·부싯돌과 부시로 간다. 음식은 `Survival`이 먹는다. TNT는 아직 쓰지 않는다.
일반 루트에서도 20칸 안에 보인 상자(마을, 폐허 포탈, 난파선)는 철이 모자라면 연다.

**하네스.** `run_batch.py --jvm-arg`(예: `-Dsrb.probe=true`), `--port-base`(배치 여러 개 동시 실행 시 포트 충돌 —
실제로 결과를 잃었다), 진행도 점수는 루트 공통 구간만 센다(`CORE_SPLITS`), `tools/group_report.py`(시드 그룹·루트별
요약). 시드 분류용 `-Dsrb.probe=true`: 하네스가 구조물 탐색기로 스폰~난파선/폐허 포탈/마을 거리를 기록(분류 전용,
봇은 모름).

**처리량.** 틱 워프의 "틱 사이 3ms 작업 시간"이 할 일이 없을 때도 기다리는 시간이었다(`runTasksTillTickEnd`가
마감까지 park). 기본값을 0으로 바꿨다(대기 중인 청크 작업은 다음 틱 시작에 그대로 처리되므로 틱 내용은 같다).
같은 시드·같은 빌드 4000틱: 35.0초 → **21.8초(1.6배)**. 서버 1개가 약 2.3GB를 써서 15GB 머신에서는 4개가 상한이다

평가와 별개)에서 했고, 튜닝(교차 엔트로피)은 네더 진입이 0인 상태에서 "구간 도달"만 미는 것이라 이번에는 돌리지

### 10.2 찾은 것과 바꾼 것

- **네더에 들어가는 순간 서버가 죽었다.** 가짜 플레이어의 `playerTick()`을 월드의 엔티티 틱 안에서 불렀는데, 포탈
  이동은 플레이어를 월드에서 빼므로 바닐라가 "Removing entity while ticking!"으로 서버를 멈춘다. 결과 줄이 남지 않아
  `harness_no_result`로 집계됐다(후반 측정 첫 회 48개 중 7개가 실제로는 네더 진입). 진짜 플레이어처럼 네트워크
  처리 자리(서버 틱 끝, 월드 루프 밖)에서 `FakePlayer.networkTick()`으로 부른다. 2단계 평가에는 이 실패가 없었다
  (포탈까지 간 런이 없었음).
- **멈춤(감시견 발동)이 런 시간의 큰 몫이었다.** 시드 16개 진단에서 런당 12회 × 15초. 원인별로:
  계단식 하강이 물·자갈·동굴 경계에서 멈춤 → 용암을 근처에서 본 적이 없으면 1×1 수직 굴(가장 빠르고 멈추지 않음)로
  내려가고, 용암 목표에서는 물 양동이가 있으니 y 13까지 굴로 내려간다(`lava.shaftMinY`). 굴 밑이 4칸 넘게 비면
  내려가지 않고 계단·동굴로, 굴 테두리에 걸려 서 있으면 칸 가운데로 옮겨 떨어진다. 지표에서 굴 밑이 물(호수·바다)이면
  계단 대신 물 반대편 마른 땅으로 10칸+ 옮겨 다시 판다. 물에 떠 있을 때 수면 위 칸으로 "헤엄쳐 오르기"가 끝나지 않던
  이동 버그(발이 수면 위로 올라가지 않음)를 고쳐 기슭으로 나간다. 캐기 시간 제한을 400 → 200틱(감시견 300틱보다
  짧게, 그래야 호출한 쪽이 방향을 바꾼다). 멈춤 진단 줄에 발 주변 블록을 남긴다. 같은 자리에서 두 번 멈추면 멀리
  옮기는 시도(`safety.relocate`)는 효과가 없어 꺼 두었다.
- **용암 찾기.** y 12 굴은 초당 약 0.5칸밖에 못 판다(돌 곡괭이 + 5틱 쿨다운, 바닐라 그대로). 시야만으로는 굴이 동굴과
  만나야 용암이 보인다. 새로 **소리**(§2 표): 바닐라 클라이언트가 내는 용암 소리를 같은 확률로 듣고, 방향·거리의
  사람 수준 오차를 넣어 위치를 짐작한다. 두 번 이상 들으면 짐작 위치 평균 쪽으로 굴 방향을 튼다. 소리 쪽으로 기억
  지도 경로(모르는 바위를 파며 곧장)를 따라가게 했더니 보이지 않던 용암을 열어 후반 측정 48개 중 15개가 용암에
  죽었다 → 굴 걷기(앞칸·바닥 용암 검사가 있는)로만 방향을 바꾸고, 짐작 위치 3칸 안에 와도 안 보이면 그 짐작은
  버리고 둘러본 뒤 다시 듣는다. 지도 경로가 용암 웅덩이 근처에서 바닥을 모르고 아래로 파지 않게 했고(밑이 용암일
  수 있음), 용암 근처에서는 감시견의 무작위 걷기를 하지 않는다(두 런이 그렇게 용암에 걸어 들어갔다).
- **주조.** 후반 측정에서 실패를 분류해 고친 것: 곡괭이 두 개가 굴과 방을 파다 닳아 없어지면 주조가 양동이로 돌을
  "캐며" 멈췄다 → 곡괭이가 없으면 무엇보다 먼저 돌 곡괭이를 만든다. 주머니가 사방으로 동굴에 열려 용암을 부을 면이
  없으면(용암 양동이를 든 채 멈췄다가 용암에 죽음) 붓기 전에 그 터를 버린다. 물을 뜨러 움직인 뒤 그 자리에서 물을
  부을 면이 안 보이던 것 → 물 붓기·물 세워 두기도 서 있는 칸으로 돌아가서. 용암 뜨기 거리 3.6 → 4.5칸(양동이 광선은
  바닐라 5칸), 조준점을 표면 위(0.9)에서 표면 안(0.6)으로 — 위에서 비스듬히 보면 광선이 원천 위를 스쳐 지나갔다 —,
  모서리에 가리면 표면의 다른 점으로 바꿔 조준. 흑요석이 하나라도 있는 터는 길 못 찾음·캐기 실패로 바로 버리지 않고
  8번까지 다시 시도한다(전에는 5/10짜리 틀을 버렸다).
- **물.** 동굴 벽의 샘(옆이 트인 물 원천)도 뜬다(`water.springs`).
- **부싯돌은 나중에(`route.flintLate`).** 전체 런 첫 측정에서 부싯돌 단계(y 50 굴에서 자갈 찾기)가 11개 런을 끝냈다.
  점화는 틀이 다 선 뒤에만 필요하므로 양동이 → 물 → 용암 → 주조를 먼저 하고, 내려가는 길(동굴)에서 본 자갈은 캐 두며,
  틀이 서면 그때 부싯돌을 얻어(자갈 내려놓고 다시 캐기) 부시를 만든다. 철 4개는 그대로(양동이 3 + 부시 1).

## 11. 3단계 M1 2회차

§10.4의 계획 순서대로 후반 단계(용암 찾기·주조)의 실패를 하나씩 trace로 확인하고 고친 뒤, 앞 단계와 전체 런을
다시 쟀다. 개발은 평가 시드와 겹치지 않는 개발 시드(`tools/seeds_dev.txt`, 48개 중 앞 24개)에서 했다.

### 11.1 하네스

- **봇 jar가 두 개 실린 슬롯.** `run_batch.py`가 `--mod`로 준 jar를 원래 파일 이름 그대로 슬롯의 `mods/`에 복사하고
  `speedrun-bot*`만 지웠다. 이름이 다른 jar(`r2a.jar`, `r2b.jar`…)로 배치를 돌리면 이전 jar가 남아 같은 모드가 두 번
  실렸고 로더가 그중 하나(옛 코드)를 골랐다. 이번 회차 첫 두 측정이 그렇게 오염됐다. 이제 `mods/`의 jar를 모두 지우고
  `speedrun-bot.jar` 한 이름으로 복사한다.
- **서버 시작 시간.** 1.16.1 서버는 시작할 때마다 데이터 픽서(옛 월드 변환 규칙)를 워커 스레드에서 수십 CPU초 동안
  최적화한다. 런마다 새 월드라 변환할 것이 없으므로 그 최적화를 건너뛴다(`mixin/SchemasMixin`, LazyDFU 모드와 같은
  방법, 게임 동작과 무관). 4개 병렬에서 후반 단계 24런 배치가 약 30분 → 15분.

### 11.2 찾은 것과 바꾼 것 (후반 단계)

- **꼭대기 두 칸의 물이 안 부어짐**(시간초과의 큰 몫: 흑요석 9/10에서 2~4분 멈춤). 서 있는 칸 옆 칸도 "닿는다"며
  받아들였는데, 옆 칸에서는 꼭대기 칸 앞의 물을 부을 면이 방의 가장자리 블록 뒤에 가려 크로스헤어가 그 블록 밑면에만
  닿았다. 이제 면이 실제로 보이는 서 있는 칸만 쓴다: 기억 지도 위에서 눈 → 면 중심 선분이 아는 단단한 블록을 지나지
  않는지(가장자리를 스치는 선도 막힌 것으로) 검사하고, 그런 칸이 없으면 다른 서 있는 칸으로, 붓기를 면마다 세 번씩
  시도해도 안 되면 그 칸을 "안 보이는 칸"으로 표시하고 다음 칸으로 간다.
- **웅덩이 앞에서 45초 기다림.** 알려진 용암 원천이 12개 미만이면 더 큰 웅덩이를 45초 찾았는데, 실제로는 웅덩이
  가장자리에 선 채 움직이지 못했다. 이제 7칸 안의 웅덩이는 먼저 3초 둘러보고(낮은 각도에서는 원천이 적게 보임),
  둘러본 뒤에는 원천 8개로 충분하다고 본다. 큰 웅덩이 찾기 상한 45 → 20초(`portal.poolSearchTicks`).
- **용암 소리가 위에서 나는데 y 12 굴만 팜.** 소리 짐작의 높이가 2.5칸 넘게 위면 그 높이까지 계단을 파 올라간다
  (`stairUpStep`: 머리 위·앞칸 위를 파고 한 칸 올라섬, 용암 옆 블록은 안 팜). 짐작 지점에 와도 안 보이면 바로 버리지
  않고 그 방향으로 5칸 더 판다(거리 짐작은 소리 크기라 시선 방향으로 오차가 큼). 이미 보이는 용암(흐르는 용암, 샘)
  근처에서 나는 소리는 "설명된 소리"로 기억해 다시 따라가지 않는다(같은 흐름 주위를 몇 분씩 맴돌았다).
- **틀을 버리는 실패.** 물 부을 면이 없음(`no_water_face`)·주머니가 열림·같은 자리 두 번 멈춤도 흑요석이 있으면
  틀을 유지한 채 재시도(최대 8회). 방 파기 상한 2분 → 70초, 같은 자리에서 두 번 멈추면 다른 터.
- **터 고르기.** 서 있는 칸에서 4.3칸 안에 선이 트인 용암 원천 수만큼 점수를 깎아 걷지 않고 뜰 수 있는 터를 고른다
  (주조 시간의 가장 큰 몫이 용암 뜨러 오가는 것: 단계별 합계에서 "용암 가져오기" 391초 > 주머니 213초 > 붓기 130초).
- **생존.** 시야 밖에서 맞으면(좀비가 뒤·굴 위에서) 둘러보고 위도 본다. 체력 12 미만이면 배고픔 18 미만에서도 먹는다
  (2 체력, 빵 8개로 죽은 런). 돌 곡괭이와 함께 돌 검을 만든다(조약돌 2개 더); 1.16 공격 쿨다운에 맞춰 검 13틱,
  곡괭이 17틱마다 친다(아이템을 바꾸면 쿨다운이 다시 시작). 용암 3칸 안에서는 달리지 않고, 용암 옆 칸으로는 천천히
  걷는다(달리던 관성으로 웅덩이에 빠진 런).

### 11.3 찾은 것과 바꾼 것 (앞 단계)

- **바다 정찰 35초.** 스폰에 바다가 보이면 난파선을 35초 찾았다(평가 48개 중 27런). 보물 루트로 간 런은 1개뿐 →
  기본값 끔(`treasure.scoutTicks` 0).
- **나무.** 4칸 떨어져서 캐면 떨어진 원목이 줍는 거리 밖(줄기 밑)에 떨어져, 한 나무를 다 캐고 다음 나무로 가며 드롭을
  버렸다(첫 원목 split이 0:43인데 0:05부터 캐던 런). 캔 원목이 떨어질 자리를 기억하고, 그 자리에서 더 닿는 원목이
  없으면 주우러 간다(보이는 아이템 엔티티도 기억).
- **물가 오르기.** 수면에서 출렁여 발이 잠깐 물 밖이면 "땅도 물도 아님"이라 점프를 안 했다 → 발밑이 물이면 물속처럼
  점프(바닐라는 물에서 벽을 밀며 점프하면 위로 밀어 줌). 물속 바닥으로 가라앉은 것을 "경로 이탈"로 보고 매 틱 다시
  계획하던 것도 고침.
- **감시견.** 레일(광산) 위에서 두 칸 사이를 5분 왔다 갔다 하는 런이 있었다(발 칸이 바뀌어 "진행"으로 셈). 이제 진행 =
  인벤토리 변화 또는 2.5칸 이상 이동. 같은 자리에서 두 번 멈추면 그때 하던 경로 단계를 계획에서 계속 뺀다.
- **제련 중.** 자갈을 모르면 화로 10칸 안에서 자갈을 찾아 판다(부시는 틀 뒤에 필요한데 그때 찾느라 몇 분 쓴 런).

## 12. 3단계 M1 3회차

§11.6 계획대로 멈춤(감시견) 원인을 trace로 하나씩 재현해 고치고, 구조적 선택지(폐허 포탈, 마을, 지표 용암)를 데이터로
따져 본 뒤, 평가 48개를 같은 코드로 두 번 돌려 합산했다. 개발은 개발 시드(`tools/seeds_dev.txt` 앞 24개)와, 평가
시드 중 trace에 멈춤이 남은 몇 개를 같은 코드로 다시 돌려 진단하는 방식으로 했다(수치 튜닝에는 평가 시드를 쓰지 않음).

### 12.1 구조적 선택지 검토 (구현하지 않은 것과 그 이유)

시드 분류 probe(`results/probe_seeds.jsonl`, 76개 시드, 하네스가 구조물 탐색기로 잰 스폰~구조물 거리, 봇은 모름):

| 구조물 | 스폰 100칸 안 | 160칸 안 | 250칸 안 |
|---|---|---|---|
| 폐허 포탈 | 4 (5%) | 9 (12%) | 29 (38%) |
| 마을 | 3 (4%) | 9 (12%) | 14 (18%) |
| 난파선 | 5 (7%) | 10 (13%) | 17 (22%) |

- **폐허 포탈**: 1.16 실제 러너의 주요 루트지만, 봇은 본 것만 알 수 있으므로 "보여야" 쓸 수 있다. 렌더 거리 10청크
  안(160칸)에 있는 시드가 12%이고, 지형에 가리거나 묻힌 것(지하·산속 배치)을 빼면 지표에서 보이는 것은 더 적다.
  160칸을 걸어가는 데 약 30초, 빠진 흑요석은 버킷 주조(지금 틀 하나에 1~2분)나 상자 전리품이 필요하다. 지금 병목
  (용암 찾기·주조·앞 단계 멈춤)이 거의 모든 시드에 걸리는 것과 비교해 기대 이득이 작아 이번 회차에는 구현하지 않았다.
  구현 순서(다음 회차 후보): 흑요석·우는 흑요석·네더랙·마그마 블록 묶음을 본 것으로 판단 → 상자 열기(`Looter` 재사용)
  → 틀의 빈 칸 목록 → 빈 칸만 버킷 주조(`PortalPlan`을 "이미 있는 칸" 입력으로 확장).
- **지표 용암**: 평가 48개 전부 SCAN 때 용암이 보이지 않았다(`route ... lava=-1.0` 48/48). SURFACE_CAST 루트는
  그대로 두되 기대할 수 있는 몫은 거의 없다.
- **물을 지하에서**: 용암을 찾은 순간 48칸 안에 지하 물 원천을 본 런은 42개 중 6개뿐(`underground water near the lava`
  trace). 물을 먼저 뜨는 순서를 유지했다.
- **용암 굴 높이**: y 11 굴(`dig.targetY` 11, `lava.shaftMinY` 12)을 후반 단계 런 23개로 비교 — 네더 6/23(y 12는 7/23),
  용암 단계 중앙값 188초(y 12는 168초). 이득 없음, y 12 유지. 동굴 탐색 상한을 높이는 것(`cave.lavaAbove` 30)도
  7/23 vs 6/23, 몹 사망이 늘어 기본값 유지.

### 12.2 찾은 것과 바꾼 것

- **좁은 굴에서 제자리 점프(물 단계 시간초과의 주원인).** 기둥 쌓기 전에 칸 가운데로 옮기는 허용 오차가 0.25칸이었는데,
  몸 폭이 0.6이라 0.2칸 넘게 벗어나면 옆 칸 위의 블록에 머리가 걸려 0.2칸만 뛰고 블록을 놓지 못했다(디버그 줄:
  `climb phase=1 pos=… 50.2`). 0.15칸 안으로 웅크려 걸어 맞춘 뒤 뛴다(`Mover.climb`, PILLAR 걸음 둘 다).
- **자기 굴 밖으로 못 나옴.** 지표 높이(스폰 y − 2)에 닿으면 기둥 쌓기를 멈췄는데, 언덕에서는 그 높이가 아직 굴 속이라
  풀숲 쪽으로 걸어 나가려다 몇 분 멈췄다. 옆이 트일 때까지(`Mover.canStepOutHere`) 계속 쌓는다. 반대로 물이 같은 높이
  16칸 안에 있으면 쌓기를 그만둔다(물웅덩이 두 칸 옆 고사리 속에서 쌓던 런).
- **용암 소리가 아래에서 남.** 소리 짐작이 2.5칸 넘게 아래면 그 위를 "도착"으로 보고 굴을 계속 파서, 같은 소리 위를
  3분 맴돈 런이 있었다. 이제 아래로 내려가는 동굴이 있으면 그것을, 없으면 그쪽으로 계단을 판다. 계단이 스스로 돈 방향
  (물·낭떠러지)은 15초 유지한다(소리 쪽으로 곧장 되돌리다 제자리걸음한 런). 같은 소리를 네 번 놓치면 그 소리는 버린다.
- **자기 굴을 동굴로 착각.** 굴이 물에 잠기거나 옛 굴 옆을 지나면 공기 칸이 많아 동굴 프런티어로 뽑혀, 자기 굴 끝을
  3칸씩 오가며 2분을 썼다. 봇이 캔 칸은 프런티어 계산에서 바위로 친다(`Actions.dug`).
- **화로·작업대를 뚫는 경로.** 경로 탐색이 자기 화로를 캐는 비용을 보통 블록처럼 쳐서, 제련 중인 화로를 캐 광석을
  잃은 런(화로 다시 놓기 실패 → 자리 옮김 반복)이 있었다. 경로는 화로·작업대를 캐지 않는다.
- **작업대를 잃고 나무로 돌아감.** 양동이·부시를 만들 작업대가 없고 판자가 4개 미만이면 y 50에서 지표의 나무까지
  갔다(시간초과 WOOD의 대부분). 이제 판자가 없으면 64칸 안의 기억한 작업대로 걸어가고, 부시는 틀이 선 뒤로 미룬다.
- **물살에 밀린 헤엄.** 물속에서는 경로 이탈 재계획을 하지 않아, 물살에 3칸 밀린 SWIM_UP 걸음이 끝나지 않았다.
  출발 칸에서 1칸 넘게 밀리면 다시 계획한다.
- **방을 위에서 파다 용암에 빠짐.** 포탈 방 블록을 그 바로 위에 서서 캐면(발밑을 먼저 캠) 방 밑 용암 웅덩이로 떨어졌다
  (후반 런 2개 사망). 블록 바로 위 칸은 "닿는 자리"에서 뺀다(`Navigator.reach`).
- **방·주머니 블록 캐기 실패가 1초에 8번.** 흑요석 1개 뒤 같은 자리에서 캐기 실패를 8번 연속 세고 틀을 버렸다. 첫 실패는
  2.6칸 안으로 다가가서 다시 캔다.
- **스켈레톤.** 체력 12 이하이거나 10칸 넘게 떨어진 궁수에게는 달려들지 않고 시야 밖으로 피한다(물러나는 궁수를 쫓다
  15초에 화살 4발로 죽은 런).
- 상태 줄에 지금 하는 일(`act`)을 남긴다(멈춤 원인 찾기).

### 12.3 바다 스폰 루트: 파이 차트로 매장 보물 (TREASURE, 1단계 구현)

상위 1.16.1 RSG 기록 런(네더 IGT 1:43)의 바다 스폰 루트를 우선 구조 루트로 삼는다. 전체 루트:

1. 스폰에서 F3 파이 차트 + 아주 좁은 창(가로 시야 약 8°)으로 매장 보물 방향을 ~10초에 찾고 판다(철, 금, 다이아몬드,
   익힌 물고기).
2. 나무 → 곡괭이·도끼·검·삽, 철로 가위·양동이. 나무를 조금 더 베어 문을 만들고, 가위로 근처 잎을 모은다(물속 공기 주머니,
   물 막기).
3. 보트로 바다를 건너 해저 협곡("마그마 협곡": 바닥의 마그마 블록이 물 너머로 보임 — §2 물 안개 규칙 그대로)으로 가서
   그 위에서 내려 자갈 위에 문을 놓아 공기 주머니를 만들고, 자갈을 파며 내려가 바닥의 용암·물로 흑요석 포탈을 주조한다.
4. 포탈 안에서 자갈을 캐 부싯돌 → 부시 → 점화 → 네더.

이번 회차 구현(1단계): 공정한 파이 차트 감각(§2 표), 좁은 창 회전 측정(6°마다 한 번, 한 바퀴 60틱 + 창 바꾸기 20틱씩),
두 곳에서 잰 방위로 9,9 칸 고르기(`core/TreasureLocator`: 맞는 측정 수가 가장 많은 9,9 칸, 같으면 가까운 칸; 신호 없는
방향은 감점), 기존 보물 파기(`TreasureHunt` DIG·LOOT)에 연결. 스폰에서 바다(해수면 물 원천 150개+)가 보이면 이 루트를 먼저
시도하고, 신호가 없으면 3~4초만 쓰고 보통 루트로 간다. 보물 상자의 철(보통 5~8개)이 철 캐기·제련(약 2분)을 대신한다.
아직 없는 것: 문·잎 공기 주머니, 보트, 해저 마그마 협곡 찾기와 수중 주조, 포탈 안 자갈 — 다음 회차(§12.6).

### 12.4 RSG 리셋 정책과 두 가지 지표

실제 러너는 나쁜 시드를 몇 초 만에 버리고 끝난 런의 IGT만 센다. `core/ResetPolicy`가 본 것만으로 리셋을 판단한다(스폰에
나무도 바다도 없음 / 바다인데 보물 신호도 나무도 없음 / 철 4:00, 물 양동이 5:30, 포탈 터 8:00까지 못 함 — 수치는
`reset.*` 파라미터). 시드별 런은 멈추지 않고 첫 판단의 틱·이유를 결과(`reset_why`, `reset_ticks`)에 남긴다. 판단이 그
때까지 본 것만 쓰므로, "그 틱에서 시도가 끝났다"고 치는 것이 실제로 리셋한 것과 정확히 같다. `tools/rsg_report.py`가
시도당 네더 비율, 네더 1회당 시도 수, 리셋을 포함한 네더 1회당 IGT(와 리셋마다 월드 생성 몇 초를 더한 RTA 비슷한 값)를
낸다. 시드별 표(§12.5)는 이전 회차와 같은 방식 그대로다.

4. **물·나무 단계 멈춤**(timeout_WATER 14, WOOD 10): 물웅덩이 헤엄 걸음, 지하에서 나무로 돌아가는 경우 남은 것.
5. **주조 단계**: 방 파기 중 경로 실패(A* 12000 노드 소진)로 감시견까지 기다림 → 바로 다른 터; 용암 낙하 사망.
6. 생존(화살 7, 크리퍼 4): 궁수 시야 끊기 블록, 크리퍼 소리.
7. 측정은 계속 48 × 2 합산, 리셋 지표는 같은 패스에서 `rsg_report.py`로.

### 12.7 M2~M4 계획 (상위 런 기준, 아직 구현 안 함)

같은 상위 런(네더 IGT 1:43, 엔드 입장 6:32, 드래곤 ~6:44)의 흐름을 마일스톤 계획으로 적는다. 감각 규칙은 모두 §2 그대로:
파이 차트 = 절두체 안 블록 엔티티 수(위치 없음), 엔더 눈은 보이는 비행 각도만(사람 수준 각도 오차), F3 좌표 허용,
구조물 조회 없음. 코드는 `core/PieChart`·`TreasureLocator`를 블록 엔티티 종류(상자, 스포너)와 목표 칸 규칙만 바꿔 재사용하게
짰다.

**M2 네더.**
1. 들어가자마자 좁은 시야(가로·세로) + 파이 차트로 보루(bastion) 상자 방향을 ~15초에 찾는다(상자 블록 엔티티).
2. 가는 길에 상자 하나(화살, 실). 숨은 금 블록 4개 자리 옆에 먼저 피글린 함정(구덩이·블록)을 만들고 금 블록을 캔다 →
   화난 피글린이 와서 함정에 빠져 갇힌다. 금 블록 → 금괴, 갇힌 피글린에게 던져 물물교환. 다른 금 블록 4개 자리도 같은
   방식. 위쪽의 열지 않은 상자 몇 개(흑요석, 화살, 실, 금 레깅스 — 입으면 피글린 중립).
3. 요새: 블레이즈 스포너(mob_spawner 블록 엔티티)를 파이 차트로 찾고(좁은 시야), 공개 지식(1.16 보루·요새 배치 경향)만
   쓰며 진주로 이동.
4. 피글린에게 돌아와 쓸모 있는 교환품만 줍는다: 엔더 진주(눈 + 이동에 충분히), 실, 우는 흑요석, 흑요석, 네더 벽돌,
   화염 저항 물약, 영혼 가속 철 장화, 발광석 가루, 영혼 모래(M4 기둥 블록).
5. 블레이즈 막대 사냥(화염 저항 물약을 마시고, 안전한 자리에서).
- 아이템 쓰임: 실 → 양털 → 침대(M4 드래곤); 발광석 가루 + 우는 흑요석 → 리스폰 정박기(네더 스폰 설정·안전, M4 방패·폭발);
  네더 벽돌 → 네더 벽돌 블록(건축 블록: M4 기둥·폭발 가림); 영혼 가속 장화 착용; 화염 저항 물약은 블레이즈 전에.

**M3 요새(stronghold).**
1. 오버월드에서 보트에 앉아(정확한 yaw) 엔더 눈을 던지고, 좁은 시야(확대)로 비행 각도를 정밀하게 읽는다. 1.16 공개 지식
   (첫 고리: 원점에서 1280~2816칸, 요새 3개)과 합쳐 한 번(또는 두 번 던져 삼각측량)으로 위치를 짐작 — MCSR에서 허용되는
   엔더 눈 계산기(각도 → 요새 추정과 오차, NinjabrainBot식 계산)와 같은 계산을 봇이 본 각도로 한다.
2. 네더로 다시 들어가 거리의 1/8을 가고, 목표 쪽으로 진주, 그 자리에 포탈을 지어 요새 근처로 나온다.
3. 요새 안에서 본 것으로 포탈 방을 찾고 눈을 모두 넣고 엔드로.

**M4 엔드.** 흑요석 기둥 하나 근처에서 영혼 모래(교환품)와 네더 벽돌 블록으로 y 95~100까지 쌓고, 침대 자리 옆에 리스폰 정박기를 방패·발판으로
놓는다(폭발 저항). 드래곤이 지나가거나 내려앉을 때마다 침대(오버월드·엔드에서 폭발)와 정박기(발광석으로 충전, 네더 밖에서
쓰면 폭발)를 함께 터뜨려 ~15초에 잡는다. 터뜨리는 시점은 봇이 보는 것만(시야 안 드래곤 위치·접근, 소리)으로 정한다.

**M5.** 처리량·튜닝·전체 런 평가, 그리고 리셋 정책(§12.4; MCSR 허용 시드 리셋 대기열 모드와 같은 역할)으로 RSG 지표.

## 13. 3단계 M1 4회차: 바다 루트 (전략 전환)

세 회차 동안 일반 굴착 루트(물 ~4:00, y 12 하강 ~1분, 용암 찾기 2~3분, 주조 1.5~2분 → 네더 8~9분)는 구조적으로 10분
안의 완주에 닿지 못한다는 것이 확인됐다. 실제 RSG 10분 이하 기록은 좋은 시드 + 빠른 리셋 + 바다 루트에서 나온다. 이번
회차는 상위 런의 바다 루트를 처음부터 끝까지 짓고 RSG 방식(시도당 비율, 네더 1회당 IGT)으로 평가하는 쪽으로 옮겼다.
일반 루트는 그대로 두어 비교용 대체 루트로 쓴다(바다가 아닌 스폰, 바다 루트가 중간에 실패한 런).

### 13.1 바다 판단 (`core/OceanSense`)

3회차의 "해수면 물 원천 150개+"는 강·호수 스폰에서도 참이었다. 이제 본 물 원천만으로 사람이 한눈에 하는 판단을 흉내 낸다:

- 해수면(y 62 원천) 칸 수 `surface`, 그중 8칸 떨어진 8방향이 모두 해수면 물인 칸 수 `open`(열린 바다; 폭 12칸 강은 0~20),
  수면 7칸 아래 물 수 `deep`(해안에서는 낮은 각도라 거의 안 보여 기본값에서 끔), 해안 높이 모래 `beach`(기록만).
- 기본값: surface ≥ 300, open ≥ 50. 바다 시드 12개(보물·난파선 probe 시드)에서 강·호수 스폰(open 0~30)과 바다(open 169~2616)가
  깨끗하게 갈렸다. 늪은 deep을 켜야 거를 수 있는데 해안에서는 deep이 안 보여 지금은 거르지 못한다(한계).
- 테스트: `OceanSenseTest`(열린 깊은 바다 = 바다, 폭 12 강·대각선 강·늪·해수면 위 호수 = 아님, 해안 모래).

### 13.2 파이 차트 보물: 두 높이 띠와 세 번째 회전

- 창: FOV 옵션 30 + 가는 창(비율 0.27) = 가로 약 8°, 세로 30°. 3회차(가로 8°, 세로 70°)보다 세로가 좁아 깊은 상자(폐광,
  해저 유적)가 같은 방위에 섞이지 않는다.
- 회전: 낮은 띠(피치 +4°, 먼 지표 근처 상자) 60걸음 한 바퀴, 그리고 낮은 띠에서 신호가 난 방위만 높은 띠(피치 +18°)로 한 번
  더. 읽기마다 눈 높이·피치·세로 FOV를 같이 기록한다.
- `TreasureLocator`에 세로 모형: 매장 보물 상자가 있을 수 있는 높이(y 40~66, 해변 밑이나 얕은 해저 — 공개 생성 지식)를 그
  거리에서 본 피치 구간이 시야의 세로 범위와 겹쳐야 "보이는" 칸이다. 거리 정보가 생겨 같은 방위의 먼 칸·가까운 칸이 갈린다.
- 두 번째 자리에서 회전 뒤에도 최고점 칸이 2개 이상이면 그 방위 쪽 20칸 앞에서 세 번째 회전.
- 테스트: `PieChartTest.twoPitchBandsSkipDeepChestsAndKeepTheTreasure`(같은 시야에 깊은 상자가 있어도 보물 칸을 고름).
- 실측: probe가 아는 보물 위치와 같은 9,9 칸을 고른 시드가 있다(-1219659680363841169: 고른 칸 -359,-103 = 실제 위치).

### 13.3 보트 (공정성: 물리는 바닐라, 봇은 키만)

- 바닐라에서 플레이어가 탄 보트의 물리는 그 플레이어의 클라이언트가 돌린다(`BoatEntity#updatePaddles`, 누른 키는
  `ClientPlayerEntity#tickRiding → setInputs`). 봇에는 클라이언트가 없으므로 봇이 탄 보트에 한해 서버가 바로 그 클라이언트
  코드를 돌린다(`mixin/BoatEntityMixin`, `EntityMixin`: 움직임을 계산하는 쪽만 서버로). 봇은 W/A/D와 웅크리기(내리기)만
  누른다(`ServerBot.setMovement`). 보트 타기 = 크로스헤어의 엔티티 우클릭(`BotInputs.useEntity`, 바닐라 클라이언트의 엔티티
  조준 규칙), 보트 놓기 = 물을 보고 보트 아이템 사용(BoatItem이 유체까지 광선을 쏨). 감각: 탄 보트의 방향(`BotSenses.boatYaw`,
  사람이 보는 뱃머리).
- 가짜 플레이어는 보트에 탄 채로도 서버에서 자기 중력을 돌려 낙하 거리가 쌓여 "낙하사"했다 → 탄 동안 낙하 거리 0(클라이언트의
  탄 플레이어는 스스로 떨어지지 않음).
- 틱 워프와 청크 생성: 보트(초당 8칸)로 워프 속도(초당 100틱 이상)로 달리면 비동기 청크 생성이 못 따라와 보트가 아직
  엔티티 틱이 안 되는 청크에 들어가 멈추고, 봇은 보트에 탄 채 바닥까지 가라앉았다. 20 TPS의 사람 클라이언트에는 없는 일이므로,
  보트의 청크와 2초 앞 청크가 틱 상태가 아닐 때는 워프를 멈추고 보통 속도로 돈다(`ServerBot.worldReadyAhead`; IGT는 틱이라
  영향 없음).

### 13.4 마그마 협곡 찾기와 내려가기

- 생성 규칙(공개 지식): 해저 협곡·동굴은 y 10을 마그마(25%)·흑요석(75%)으로, 그 아래를 용암으로 채운다
  (`UnderwaterCaveCarver`). 마그마 위 물에는 아래로 끄는 거품 기둥이 수면까지 선다(켈프·해초가 있으면 끊김). 사람은 수면의
  거품과 물 너머로 보이는 기둥을 보고 협곡을 찾는다. 봇도 시야 광선이 지나간 거품 기둥 칸(`WorldMemory.Kind.BUBBLES_DOWN`)만
  안다 — 물 안개 16칸 규칙 그대로.
- 해저 유적의 마그마 하나에서도 기둥이 선다. 협곡은 바닥의 1/4이 마그마라 기둥이 무리로 서므로, 10칸 안에 기둥 x,z가 5개
  이상인 곳만 협곡으로 친다. 내려가다 y 20 위에서 마그마에 닿으면 그 근처를 버리고 수면으로 올라가 보트를 다시 탄다.
- 항해: 출발점을 중심으로 사각 나선(다리 48, 48, 96, 96…, 첫 방향은 열린 바다 쪽), 뱃머리 좌우 ±70°를 피치 25°로 훑는다.
  앞 10칸에 수면 높이의 땅이 보이면 다음 꼭짓점으로. 기둥이 보이면 그리로 가서 1칸 안에서 웅크려 내린다.
- 하강: 내린 자리에서 가장 가까운 기둥 칸으로 옆걸음해 들어가면 끌림(초당 ~18칸까지)으로 바닥까지 몇 초. 마그마 위에서는
  웅크린다(바닐라: 웅크리면 마그마 피해 없음; `Controls.holdSneak`, 걸을 때는 빨리 벗어나는 쪽이 낫다). 생존 모듈은 마그마·
  익사 피해를 "보이지 않는 공격"으로 보지 않고, 바다 바닥 단계에서는 공기를 위해 수면으로 헤엄치지 않는다(공기는 문 주머니에서).

### 13.5 문 주머니 (물속에서 마른 칸 만들기)

바닐라에서 문은 물이 흘러 들어가지 못하는 블록이다(`FlowableFluid#canFill`). 협곡 바닥에서:

1. 바닥 높이에서 걸어서 닿는 칸 중(위로 헤엄치기는 끌림 때문에 안 됨 → 같은 높이 BFS, 안 본 칸은 물로 침) 옆 벽이 두 겹 바위인
   자리를 고르고 그 길을 따라 걷는다.
2. 벽 첫 칸 두 블록(w1, 머리 높이 포함)을 캔다(물이 찬다). 열린 자리에서 물러난 뒤, 벽 쪽을 보고(문은 놓는 사람이 보는 방향으로
   선다) w1 바닥 블록 윗면에 문을 놓는다 — 물이 차 있던 두 칸이 문이 된다.
3. 문을 연다(웅크린 채 아이템을 들고 우클릭하면 블록에 닿지 않는다는 바닐라 규칙 때문에 웅크리지 않고). 열린 문 너머로 두 번째
   칸 두 블록(w2)을 캔다: 이웃이 문과 바위뿐이라 물이 들어오지 않는다.
4. 열린 문의 판이 칸 한쪽에 붙어 있어 빈 폭이 0.81칸, 몸 폭이 0.6칸이므로 블록 충돌 상자로 빈 쪽 가운데에 줄을 맞춰 들어간다.
   w2에 서면 마른 칸(공기 회복). 그 뒤 봇은 바다 밑에서 물을 막고 있는 블록, 문, 문을 받치는 블록을 캐지 않는다
   (`Actions.keepWaterOut`, `Navigator` 비용도 같은 규칙).
5. 그다음은 일반 목표가 이어받는다: 물 양동이(항해 전 바다에서 떠 둠), 용암(소리·동굴 탐색), 포탈 터, 주조, 부싯돌.

개발 고정 장면(`-Dsrb.devStart=ravinefloor -Dsrb.devOcean=WALL`, 시드 4689709432956513359)에서 바닥 도착 → 마른 주머니까지
약 18초(공기 62/300 남음). 협곡 바닥 밑 용암을 주머니에서 직접 여는 단계(대각선 아래로 열어 흐름이 봇에게 오지 않게)는 문을
받치는 블록이 시선을 가려 실패해 이번에는 빼고, 일반 용암 찾기(소리)에 맡겼다 — 같은 장면에서 2:00에 용암을 듣고 2:20에 포탈 터를
잡았지만 주조 중 용암을 놓쳤다.

### 13.6 루트 순서와 리셋 정책

바다 스폰(13.1) → 파이 차트 회전(~8~12초, 13.2) → 보물 칸이 물 건너면 나무(판자 16) → 작업대에서 보트·문 → 보트로 보물 칸 근처
→ 파서 상자 → 나무(판자 16) → 철 곡괭이(철 7개 이상, 아니면 나무 곡괭이)·양동이·보트·문 → 해안·얕은 바닥 자갈 3개(부싯돌용,
바다 밑에서는 모든 자갈이 물에 붙어 있어 캘 수 없다) → 양동이에 바닷물 → 보트 → 협곡 → 하강 → 문 주머니 → 일반 목표.

RSG 리셋 정책(`reset.oceanOnly` 1, 기본): 스캔 뒤 바다가 아니면 리셋(`spawn_no_ocean`), 회전에서 상자 신호가 없으면 리셋,
보물을 2:00까지 못 열면, 협곡을 4:00까지 못 찾으면, 7:00까지 네더에 못 가면 리셋. 판단은 그때까지 본 것만 쓴다. 시드별 런은
3회차처럼 계속 돌고 판단만 기록하며, 풀 측정용 `-Dsrb.rsgStop=true`는 판단하는 틱에 런을 끝낸다(새 월드를 만드는 사람과
같음; 바다가 아닌 스폰은 IGT 4초에 끝나 풀 처리량이 크게 는다).

### 13.8 남은 격차와 다음 일 (바다 루트, 우선순위 순)

이번 회차에 바다 루트의 뒤쪽 절반(보트, 협곡 찾기, 하강, 문 주머니)은 고정 장면에서 끝까지 동작하게 됐지만, 앞쪽(보물)이

1. **보물 파기**(지금 병목): (a) 칸 정확도 — 두 번째·세 번째 회전 자리를 보물 방위에 수직으로 더 멀리(40칸+), 회전을 보트
   위에서(헤엄 없이) 하기; (b) 파는 속도 — 돌 밑이면 나무 곡괭이(지금은 판자가 모자라 실패: `ocean.boatPlanks`를 올리거나 막대
   먼저), 모래·자갈은 손으로; (c) 칸에서 12칸 내려가도 없으면 이웃 칸 하나만 보고 포기 → 회전을 다시. (d) 상자를 열고도 빈손으로
   나온 런(`inv=sand`) — Looter가 보물 상자 화면에서 무엇을 가져오는지 확인.
2. **물가 오르기**: 바다에서 1칸 턱 위로 못 올라 몇 분 멈추는 런(SWIM_UP 반복)이 바다 시드마다 있다. 보트로 해안까지 붙인 뒤
   내리기, 또는 Mover의 물→땅 걸음(턱을 향해 점프+전진) 수정.
3. **해변의 나무**: 바다 스폰 근처에 나무가 적어 판자 16개에 1~2분. 숲 방향 판단(본 잎·원목 무리)과 리셋 기준에 "나무 없음" 추가.
4. **협곡 바닥 밑 용암 열기**: 주머니에서 바로 아래(바닥 y 10 밑 용암)를 흐름이 봇에게 오지 않게 여는 방법 — 주머니를 한 칸 더
   파고 들어가 (문 받침과 떨어진 곳에서) 대각선 아래로 열기, 또는 보물 철로 양동이 하나를 더 만들어 물을 부으며 열기. 지금은 일반
   용암 찾기(소리)에 맡겨 1~2분이 더 든다.
5. **문 레시피 실패**: 보물 전 보트·문 제작에서 문이 "알려진 레시피 0"으로 나온 런이 있어 문을 선택 항목으로 돌렸다(보물 뒤에
   다시 만든다). 원인(레시피 북 해금 시점) 확인 필요.

## 14. 3단계 M1 5회차: 바다 루트 앞쪽 (보물)

4회차 끝에 바다 루트의 뒤쪽 절반(보트 → 협곡 → 문 주머니)은 고정 장면에서 동작했지만, 실제 시드에서 보물 단계가 한 번도 끝나지
않았다. 이번 회차는 §13.8의 순서대로 보물 단계를 단계별 고정 장면으로 하나씩 고치고, 실제 시드(전체 런)와 RSG 풀로 확인했다.

### 14.1 측정 도구

- 고정 장면 `-Dsrb.devStart=treasure -Dsrb.devTreasure=true`(개발 전용, 측정 아님): 하네스가 구조물 탐색기로 가장 가까운 매장
  보물 칸 위에 봇을 두고, 봇은 발밑 칸을 판다. 결과 JSON의 `dev`에 실제 상자 높이와 칸의 블록 열(위 10칸)을 기록한다.
  보물 시드 10개의 열: 상자는 언제나 모래 2~3칸 밑, 사암·돌 바로 위; 위의 물 깊이는 0~30칸(y 32~62).
- `-Dsrb.dumpPie=true`: 회전 읽기 전부를 trace에 남기고, `pie_an.py`(작업용 스크립트, 저장소 밖)로 실제 보물 위치와 비교해
  후보 순위 규칙을 오프라인에서 비교했다.

### 14.2 찾은 것과 바꾼 것

- **물속에서 웅크려도 가라앉지 않았다(물리 버그).** 바닐라에서 물속 Shift로 가라앉는 것은 클라이언트 코드(`knockDownwards`)인데
  가짜 플레이어 서버에는 그 코드가 없었다. 봇 몸에 같은 동작을 넣었다(§2). 이것 때문에 물속 보물 파기가 공중에 뜬 채(채굴 속도
  1/25)였고, 협곡 하강·주머니 단계의 "가라앉기"도 실제로는 중력만이었다.
- **보물 파기**(`TreasureHunt.dig`): 칸 가운데에 맞춰(시선은 아래, 이동 키로 미세 조정) 다음 고체 블록을 캔다. 물속에서는 웅크려
  바닥에 서서 판다. 돌·사암 등(§2 바닥 규칙)이 나오면 그 칸이 아니다. 바닥이 수면에서 16칸(`treasure.maxDepth`)보다 깊으면 한
  숨에 못 하므로 포기(러너는 리셋). 나무 삽(판자 3)을 보트와 함께 만들어 모래를 손의 두 배 속도로 판다.
  고정 장면 10개: 보물 연 런 4/10(4회차 코드) → **7/10**, 열기까지 8~15초(1개 116초). 나머지 3개는 23칸 이상 깊은 보물.
- **물속 상자 열기**(`Looter`): 손이 닿으면 헤엄쳐 "설 칸"을 찾지 않고 그 자리에서 연다(스페이스·Shift 없이: Shift + 손에 아이템이면
  상자가 안 열린다). 철부터 가져온다(철 → 지도·도구 → 음식 → 부싯돌·흑요석 → 금). 상자 화면이 열려 있으면 공기 10, 파는 중이면
  40까지 버틴다(전에는 100에서 수면으로 올라가 화면을 닫고, 다시 내려오지 못했다). 4회차의 "빈손(`inv=sand`)"은 화면이 이렇게
  닫힌 런이었다.
- **레시피 "0개 알려짐"**(§13.8-5): 바닐라는 새 재료를 가졌을 때 *플레이어 인벤토리 화면 핸들러*가 그것을 볼 때 레시피를 해금한다.
  작업대 화면이 열린 채로는 해금되지 않으므로, 없으면 화면을 닫았다 다시 연다. 보트 레시피는 물에 들어가 본 뒤에야 해금되므로
  (발전 과제 `in_water`) 손으로 격자에 놓는다(§2). 4회차의 문 실패와 이번 회차 첫 실험의 "보트 제작 실패 무한 반복"이 이것이었다
  (작업대 실패가 `bench.run(null)` 경로에서 버려져 다시 시도만 반복하던 것도 고침).
- **물가 오르기**(§13.8-2): 헤엄치는 사람의 발은 수면 0.4칸 밑에 떠 있고, 바닐라의 물 밖 점프 보조(`LivingEntity#travel`: 옆이 막히고
  0.6칸 위가 비면 위로 0.3)는 물과 같은 높이의 둑만 넘는다. 수면 위 칸(물 위 공기)에서 한 칸 높은 둑으로 오르는 걸음(UP·기둥)을
  길찾기에서 뺐다 — 같은 높이의 해변을 찾거나 둑 블록을 캔다.
- **순서**: 첫 회전(스폰) → 나무가 보이면 바로 나무·보트·문·삽(작업대는 들고 감) → 두 번째 회전은 첫 방위의 옆 40칸(`treasure.sideDist`)
  바다 위(보트로 가서 내려서, 탄 채로는 시선이 뱃머리 ±105°로 묶임) → 세 번째 회전은 두 회전의 선 밖, 지금까지 최고 칸 쪽 → 후보 칸
  **확인**: 보트로 칸 바로 위(1칸 안)에 가서 좁은 시야로 칸을 내려다본다(y 58·42 두 번). 상자 조각이 보이면 판다, 아니면 다음 후보
  (`treasure.verifyMax` 4, 35초 안에 못 가면 건너뜀). 옆에서 비스듬히 보는 확인은 같은 방위 뒤쪽의 먼 상자에 속아 뺐다. 회전 사이에
  다른 일을 하면 창을 되돌렸다 다시 좁히는 40틱을 물린다.
- **후보 점수**: 바다에는 상자가 많다(해저 유적·난파선·다른 보물). 회전 자리마다 한 번만 세는 "동의한 자리 수"(`placeVotes`)를 먼저
  보고, 같으면 읽기 수(4회차 점수). 오프라인 비교(실제 위치를 아는 3개): 이 순서에서 실제 칸이 1위 2개, 남은 1개는 26칸 앞 y 40의
  깊은 보물이라 어느 회전에도 안 보였다. 같은 표수에서 "가까운 순"은 실제 칸을 3~10위로 밀어 쓰지 않는다(`treasure.nearestNext` 0).
- 그 밖: 리셋 기준 `ocean_no_trees`(첫 회전 내내 원목 0개), 물 칸에도 작업대 놓기(보물 구덩이 안), 보트는 3×3이 트인 물에만 띄우기
  (`BoatItem`은 1.4칸 상자가 들어갈 자리가 아니면 거절), 남은 제작에 필요한 판자만 모으기(4회차는 16개 고정이라 나무로 되돌아가는
  고리), 보트를 내린 자리 기억(사람처럼; 보이지 않으면 그쪽을 본다), 수영 달리기(§2 규칙, 평영의 두 배).

### 14.4 남은 격차와 다음 일 (우선순위 순)

이번 회차에 보물 단계의 기계적인 부분(파기·물속 상자·레시피·물가·보트 띄우기)은 고정 장면에서 대부분 동작하게 됐지만, 실제 시드에서
"어느 칸인가"(위치 추정)가 병목으로 남았다. 바다 루트 네더 진입은 실제 시드에서 아직 0(고정 장면 1)이고, 목표(≤3:00)까지는 멀다:
지금 시드에서 보물을 여는 시점이 잘 돼도 2:30~3:00이고, 그 뒤 협곡·하강·주머니·용암·주조에 2분 이상이 든다.

1. **보물 위치 추정**(지금 병목): (a) 후보를 확인할 때 "못 감(35초)"이 많다 — 내륙 쪽 후보는 보트로 못 가므로 육지 길 찾기와 섞어
   가장 빠른 쪽으로; (b) 회전을 더(네 번째 자리), 또는 사람 러너처럼 첫 방위를 따라 가며 짧은 회전을 반복해 방위가 크게 돌 때 가깝다고
   판단(homing); (c) 깊이 정보: 한 자리에서 피치 여러 단을 써 거리/깊이를 갈라 깊은 보물(해저 30칸)을 처음부터 거르기.
   `-Dsrb.dumpPie=true` 기록으로 오프라인에서 규칙을 먼저 비교할 것(전체 런보다 수십 배 빠름).
2. **깊은 보물**: 해저 20~30칸 보물이 흔하다(고정 장면 10개 중 3개). 바닥에 문을 놓고 문 칸에서 숨 쉬기(4회차 문 주머니 코드 재사용)
   + 삽이면 한 번 잠수로 가능할 것.
3. **협곡 바닥에서 떠서 캐기**: 하강 직후 바닥에 서기 전에 벽을 캐면 1/25 속도 → 웅크려 바닥에 선 뒤에만 캐기. 익사 방지(공기 60
   밑이면 주머니를 서두르거나 위로).
4. **나무·보트 시간**: 보트까지 40~80초(사람 상위 런은 30초 안). 숲 방향 판단과 잎 사이 원목 캐기.
5. **협곡 바닥 밑 용암**(§13.8-4)과 **자갈(부싯돌)**: 그대로 남음. 바다 루트가 바닥에서 실패하면(벽 없음·주머니 침수) 봇은 일반 목표로
   넘어가는데, 마그마 위 거품 기둥 안에서는 위로 헤엄칠 수 없어 익사한다 → 실패 시 먼저 기둥 밖으로 옆걸음한 뒤 수면으로. 벽 자리
   고르기는 머리 높이 벽이 아직 안 보인 경우가 많다(둘러보기 피치를 0°/20° 번갈아 하도록 바꿈; 안 본 칸을 바위로 치면 주머니가
   잠겨 되돌렸다).
6. 그다음 리셋 기준을 실제 분포로(보물 2:00은 지금 너무 이르다: 풀 측정은 `reset.treasureBySec` 200으로), 그리고 §12.7의 M2.

**한계(정직하게)**: 보물 단계의 성공은 회전 결과(봇의 무작위 광선 순서와 회전 자리)에 따라 런마다 다르다. 고정 장면 수치는 측정이
아니라 단계별 동작 확인이다. 수영 달리기는 서버에서 클라이언트 규칙 하나(시작 조건)만 옮겼고, 실제 클라이언트의 다른 달리기 해제
조건(배고픔 6 이하 등은 이미 있음)과 한 틱 다를 수 있다.

## 15. 3단계 M1 6회차: 오프라인 파이 차트 시뮬레이터와 이른 리셋 판단

  확인에서 상자가 안 보이면 리셋(`ocean_no_treasure`). 시뮬레이터에서 바다 스폰 102개: 5회차 규칙 대비 시드당 쓰는 시간 약 200초 →

  거리 감점, 확인 2개는 모두 보물당 시간이 더 길었다(`--opt rule=nearest|dpen20`, `verify=2`, `sweeps=3`).

  지나므로 칸 밑 상자는 둘 다에 보이고, 몇 칸 옆의 깊은 상자(던전·유적)는 한 띠에만 보인다(§2 표 "보물 칸 확인", 감각은 같은
  절두체 안 상자 수뿐). 시뮬레이터에서 거짓 확인 24 → 0~1.

  수영 달리기(평평한 시선, 공기가 모자라면 위로). 두 번째 회전 자리까지 20~45초 → 10~20초, 후보 칸 "못 감"이 줄었다.

### 15.4 리셋 정책 (네더 1회당 IGT 기준)

네더 1회당 IGT(리셋 포함) = (시도당 평균 IGT × 시도 수) / 네더 수. 바다가 아닌 스폰은 4초에 리셋하므로, 바다 스폰에서 쓰는 시간이
거의 전부를 정한다. 5회차 정책(보물 판단 기한 200초, 바다 스폰마다 보트까지)은 바다 스폰당 ~200초, 이번 정책은 ~80초를 쓴다.
풀 400의 실측으로 네더 1회당 시도 수를 아직 낼 수 없지만(네더 0), 바다 스폰 하나의 기대값으로 비교하면: 바다 스폰이 네더로
이어질 확률 p(보물 × 협곡 × 바닥 이후)가 같을 때 이른 리셋은 시간을 2.5배 덜 쓴다. 보물이 확인된 뒤의 기한(협곡 4:00, 네더 7:00)은
그대로 두었다. 난파선을 보면 보물 대신 난파선의 철로 가는 정책은 시뮬레이터 표에서 난파선 보물 상자가 100칸 안에 있는 바다 스폰이
5/102로 매장 보물(9/102)보다 적고, 물속 상자 찾기·열기가 더 오래 걸려 이번에는 넣지 않았다.

### 15.5 남은 격차와 다음 일 (우선순위 순)

1. **후보 칸까지의 이동**(지금 병목): 물가·얕은 바다·모래톱에서 초당 1~2칸. 두 번째 회전 자리부터 후보까지 사람은 15초에 가는 거리를
   35초에 못 간다. (a) 물 위에서 보트 없이 수영 달리기를 끝까지 유지(지금은 둑·얕은 바닥에서 경로 탐색으로 넘어가며 멈칫), (b) 얕은
   바다(깊이 1~2)는 걷기로, (c) 시뮬레이터에 실제 이동 속도 모형(물/땅/둑)을 넣어 `earlyRange`를 다시 고르기.
2. **협곡 바닥 판정**: 하강 중 선반(y 15~20)을 바닥으로 보지 않기(마그마/흑요석 y 10 규칙을 이미 아니까 y < 12만 바닥), 벽 없는 넓은
   바닥에서는 바닥에 문 하나만 놓고 그 칸을 주머니로 쓰기(열린 문 칸은 마른 칸).
3. 하강 중 기둥 가장자리 턱에 걸림(이번에 둘러 가기·캐기 추가, 실전 확인 필요), 보트 띄우기 실패 재시도(추가, 확인 필요).
4. 보물 구덩이 탈출(땅 위 보물을 판 뒤 1칸 구덩이에서 2분 멈춘 런: 기둥 쌓기 대신 계단으로).
5. 그다음 실제 네더 진입이 나오면 §12.7 M2.

**한계(정직하게)**: 이번 회차에 실제 시드에서 바다 루트 네더 진입은 아직 0이다(고정 장면 1/4, 5회차). 이른 판단은 시도당 IGT를 크게
줄였지만, 보물을 찾는 바다 스폰 비율이 낮아(풀 2.5%) 네더 1회당 시도 수는 수백 이상으로 보인다. 10분 목표까지는 네더 이후
M2~M4가 전부 남아 있다.
